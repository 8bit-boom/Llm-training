# Tune this PC for this model (auto-tune and presets)

Plan: `AUTOTUNE_PRESETS_PLAN.md` (planning notes). Code: `crates/ndforge-core/src/tune/`. Owner's request: press ONE button, every setting of the Heal card is tested for the selected model, the winners are applied after one confirmation, and the settings are saved as a preset that can be selected later.

## Identity (`tune/identity.rs`)
* `shape_id` (`s-` + 16 hex) is the hash of the canonical speed-relevant facts of `config.json` (architecture, layer count and types, widths, heads, linear-attention sizes, vocabulary, tied embedding, vision/MTP/pre-quantized flags). Key order and spacing never change it. **Speed depends on the shape, not on the weight values**, so a healed or merged copy of a cut has the cut's shape.
* `weights_id` (`w-` + 16 hex) hashes `config.json` and, per `*.safetensors`, the name, size and header: no modification times. It tells entries apart; it never gates reuse.
* `shape_of_plan` gives the shape a planned cut will have (layers kept, new width), as the worker's `fix_config` writes them, so Auto-cut can find a preset before the cut exists.
* `MachineId.key` is the card's name and memory only; driver, torch, transformers, peft, bitsandbytes, triton, fla, vLLM and llama.cpp versions are `software` facts that make single results stale.

## Presets (`tune/preset.rs`, `tune/store.rs`)
* A preset (`format: 1`) holds the model identity, the machine, the tested functions (`heal.student_batch`, `heal.loss`, ...), and the WHOLE Heal card as tested (`card`), so it can be applied as a whole. Each function has `chosen` and `default` values, the gain, the measured spread, its class and tier, the guards that were checked, every candidate that was tried (an out-of-memory is a row), what it `depends_on`, which knobs are `transferable` to another model, and the `context` (sequence length, method, rank ...) it assumed. Unknown fields are kept (`extra`), so a later program version can add some.
* Where: `<project>/tune/presets/<id>.json` and the app-wide `<config folder>/tune_library/<id>.json`. Neither folder is a Storage root. A file that cannot be read is set aside as `.broken-<time>` and listed; a preset of a newer format is left where it is and listed.
* Matching, best first: **exact** (same weights and machine), **same shape** (the speed should be the same), **from a parent** (only the transferable knobs), **nearest** (same architecture within 0.67 to 1.5 times the size; transferable knobs, re-test recommended); **another PC** is listed and never offered.
* Stale: a function is stale when a component it depends on changed (driver major, a package's minor, the vLLM image, the llama.cpp version). Age alone never makes a result stale. A component that is not known now is not a change.
* Delete needs the preset's exact name typed. Export writes `<name>.ndtune.json` (`{"ndtune": 1, "preset": ...}`, the home folder replaced by `~`); import goes to the library, refuses a newer format, and needs `overwrite` for an existing id.

## The window (step 3)
* **Preset bar** (Heal card, top of "Healing settings"; the Tune page): a dropdown of the presets that fit the model (name, match kind, "stale, re-test?"), and the buttons Use…, Save current as preset…, Rename, Duplicate, Delete (type the exact name), Export, Import. Use… shows the changes against the card with the measured gain per change and "Apply all"; nothing changes before that, and nothing is saved until the card's own Start.
* **Commands** (camelCase keys, all arguments required): `tune_presets(model)`, `tune_preset_save(model, name, scope, card)`, `tune_preset_rename(id, scope, name)`, `tune_preset_duplicate(id, scope, name)`, `tune_preset_delete(id, scope, confirm)`, `tune_preset_export(id, scope, path)`, `tune_preset_import(path, overwrite)`, `tune_apply_preview(presetId, scope, model, current)`.
* **Why a button is off**: every button of the bar and the vLLM check buttons on the Heal card carry the reason in their tooltip ("Off because a job is running") and a line under the row names the job. The earlier "dim button with no reason" was `busy || running`, which did not know about Measure heal speed or a job started elsewhere; the reason now comes from the program's own busy flag as well.

## Using a preset (step 4)
* **Heal card:** "Use…" previews the changes and "Apply all" fills the card's own fields; nothing is saved before the card's Start. **Settings targets** (`tune_apply(presetId, scope, model, target, token)`, target `settings_teacher` or `settings_vllm`) change the saved settings and need the token of a fresh preview (a stale or missing token changes nothing). The teacher target takes only `teacher_batch_tokens`; the vLLM target only `max_num_seqs`, `vllm_batch_tokens` (engine `batch_tokens`) and `gpu_util_pct`. The vLLM numbers are sent to the worker only when set (a legacy job is byte-identical) and are not part of the cache identity.
* **Auto-cut:** `AutoSpec.tuned` is a SNAPSHOT of a preset (values and measured numbers) taken at Start, so a later edit never changes a running run. Only the speed knobs reach the heals (`student_batch_tokens`, `kl_chunk`, `head_checkpoint`, `checkpointing`); the quality knobs of a preset (sequence length, rank ...) are for the Heal card. The time estimate uses the measured tokens/s (a tenth less for saving and checking, as for a speed test of the loss settings) instead of the formula or the old history: the "train" part's basis becomes `your_history`.
* **Ladder:** `plan::heal_next_safer` halves `student_batch_tokens` first (down to 512, then one row per forward pass), as the worker does; both read the cases in `worker/tests/data/heal_cases.json`.

## The runner: "Auto: test and choose the best settings" (step 5)
* One big button on the Tune page, and a shortcut on the Heal card (the preset bar). It runs the ticked tests one after the other, ordered by value (tier 1 speed and memory, tier 2 quality, tier 3 other functions), keeps `<project>/tune/runs/<id>/state.json` after every test (Stop and Continue; a test that was running starts from its beginning), and at the end saves a preset ("Tested <date> (<model>)") and writes `benchmarks/tune-<id>/tune_report.{json,md}`. The window then shows ONE confirmation, "Apply and save preset", with every change and its measured gain (default button "Apply all"); applying fills the Heal card, nothing else.
* Before Start: the time per test and in total with "done around", an "I have at most N hours" cap (tests are dropped from the end of the order), and every test ticked by default that this version can run; tests that cannot run say why. A test whose card does not have the memory free waits (`waiting_gpu`) and says which programs hold it; **nothing is ended for it** (the Memory panel's Free GPU is the person's click).
* Tests built: `heal.student_batch` (the token-budget sweep of Measure heal speed on real rows, with repeats that measure the noise and a worst-case update for the peak memory; out-of-memory prunes the larger budgets) and `heal.loss` (the existing Find the fastest loss settings). Decisions (`tune/decide.rs`, pure): a candidate must fit below 90 % of the card, give the same first-update loss within 1e-3, and beat the default by more than max(5 %, twice the measured spread); within the noise the lower peak memory wins; otherwise "within noise (±x %): the default stays". The constants are pinned against `healspeed.py` by a test.
* Worker additive bench keys: `sweep_repeat`, `worst_case` (inside the existing `distill` bench; no new job type, event or error code).

## Tier 2: the quality trials (steps 6 to 8; `tune/quality.rs`, `heal_bench::trial`, worker bench key `trial`)
* `heal.quality` runs ONE short REAL heal per setting (job `distill` with `bench.trial {tokens}`; the heal's own job with `hyper` replaced: rank + alpha, optimizer, warmup, lr, seed) on the person's real rows, from the original's saved answers (so the model needs a heal or a Try first before; with synthetic answers the loss would mean nothing). The same seeded rows and the same held-out rows for every setting; the result is the held-out loss before and after (`held_before`, `held_after`).
* Variants: the baseline TWICE (two seeds: the noise), then one knob at a time from the card: LoRA size 16/32/64/128, the other optimizer, warm-up 0/10/30/100, learning rate x0.5 and x2. A value wins only when its held-out loss is lower than the baseline mean by more than max(2 x the baseline's seed-to-seed spread, 1 % of the loss) and its peak stays below 90 % of the card. When two or more knobs win, they are tried TOGETHER once (`combined`, seed 1): they are kept together only when the combination beats the baseline by the same margin and gets at least 90 % of the best single gain; else only the best single knob stays and the others say they did not add up. A combination that failed does not remove a winner and says it was not confirmed.
* Honesty: class `quality`, tier 2, every note and the table say "based on a short trial, not a full heal". There is NO final quick thinking check of the tuned settings in this version: a thinking check needs a healed model and a trial does not keep one. The thinking check on the real heal stays the gate.
* Auto-cut never takes the quality knobs of a preset (they came from a short trial); the Heal card does.

## More tests (step 9 onwards)
* `teacher.standard`: the original's answers per forward pass. Worker bench key `teacher_sweep` (loads the original as the heal does, answers the same real rows at 0 (= the fixed 4 rows), 4096, 8192, 16384, 32768, 65536 tokens, with repeats for the noise and the top-1 negative log-probability of the first window as the equivalence number). Decided by `decide_sized`: the winner must beat the budget the person has NOW (Settings `teacher_batch_tokens`) by max(5 %, twice the noise), else it stays. Saved as `teacher_batch_tokens` (a program setting, target `settings_teacher`; an Auto-cut run with a preset that chose it passes it to the cache step of each heal: `HealSpec.teacher_batch_tokens`, not part of any cache key; a heal in rounds still reads the saved setting).
* `teacher.vllm` (opt in, only with vLLM switched on): worker job `vllm_teacher_tune`. ONE reference (the heal's complete standard cache when there is one, else the standard 4-bit teacher on the same rows, freed before any container starts), then the same rows through the engine once per variant: the baseline twice, `max_num_seqs` 16/32/64, `batch_tokens` 16384/32768/65536, `gpu_memory_utilization` 80/88/92 %. Every variant is a row with speed and top-1 agreement / KL against the reference. A setting wins only when it beats max(10 %, twice the noise) and its answers agree with the reference as well as the person's settings do (top-1 within 0.5 points, KL within +0.005) and the engine got the share it was asked for. Each setting alone, never tested together (the note says so). `run_chunk` always stops and removes its container; stale `ndforge-vllm-*` containers are removed first (`memory::remove_stale`, never while a job holds one) and `stop_leftovers` runs at the end. Saved as `max_num_seqs`, `vllm_batch_tokens`, `gpu_util_pct` (target `settings_vllm`).
* `try.calib_batch` and `think.batch`: worker job `tune_batch_bench` (`what` calib | think). `calib` loads the ORIGINAL once and measures the Try-first calibration (`reshapejob._measure`) at 0 (= 4), 1, 2, 8, 16 rows together with the mean token loss as the equivalence number (class "same within tolerance"); `think` asks 16 thinking-check questions of the CUT model at 0 (= 8), 4, 16, 32 together with one seed (class "same on average": sampling makes it statistical). Saved as `try_calib_batch` / `think_batch` (target `settings_forward`); the measuring job (`calibration.batch`) and the thinking check (`batch`) read them only when set.
* `llama.offload` (tier 3): worker job `llama_offload_tune` runs a short `llama-imatrix` pass on the largest 16-bit GGUF of the project (an export's, or a Compare-quants reference) with `-ngl` from all layers (99) down (3/4, 1/2, 1/4, 1/8, none) and stops at the first that runs. The default stays when every layer fits. The number is saved as `llama_ngl` (target `settings_llama`; empty = 99) and is read by the importance matrix and Compare quants jobs. The offload was timed on that ONE file: it is a guide for the others, not a measurement of them. UNVERIFIED against a real llama.cpp: the output format ("N seconds per pass") is parsed when present, else the whole run is timed.
* `disk` (tier 3, opt in): writes and reads back 2 GB on the drive of the models (`tune/disk.rs`); decides nothing, the numbers go into the preset and the report; the read may come from the system's cache. No estimate uses it yet.
* NOT built: a fine-tune speed test (the Train page's own "Measure speed" works on a catalog model and method that an Auto run for a made model does not know), a final thinking check of the tuned settings, and tests of sequence length, batch, per update, checkpointing, method, top-k and the teacher load (they change what is learned or how it is trained).
* The final confirmation shows the Heal-card changes AND the program-setting changes (each applied with the token of its own fresh preview; `tune_apply` targets `settings_teacher`, `settings_vllm`, `settings_llama`, `settings_forward`). A preset's Heal-card preview never lists a program setting.

## The Auto page (step 4 of the window)
* "Use tested settings for this PC" lists the presets of this PC with their measured gains; the note says what the heals of the run take (the speed knobs and, only when a test chose it, `teacher_batch_tokens`), which quality knobs it does NOT take, and which program settings are saved from the Tune page. The shortcut button on the Auto page and the one on the Heal card start the same one-click Auto as the Tune page (`tuneAutoFor`).
* The time estimate uses the measured student tokens/s of the preset; the original's answers part still uses the formula or the history (the measured teacher speed is not fed in).
